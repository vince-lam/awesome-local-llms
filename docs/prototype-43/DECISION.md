# README funnel decision for [llmrepos-web #43](https://github.com/vince-lam/llmrepos-web/issues/43)

Prototype only. Compare [A: site landing](README-a-landing.md), [B: weekly lead](README-b-weekly.md), and [C: directory first](README-c-directory.md). Each uses the same 7 September 2026 table snapshot so the top section can be judged in context. **Choose A.** It explains the current division of labor in one screen: GitHub holds useful weekly rankings; LLMRepos has the full daily index, search and growth trends. B puts an unbuilt editorial feed first. C makes the visitor navigate before explaining the site's value. The existing README already has a large demo GIF and badges; A reduces that opening clutter without turning the open-source list into an ad.

## Follow-up ranking decision, 19 September 2026

Replace the single top-100 table with three generated views: 20 established leaders by total stars, 20 projects with the largest absolute seven-day star gains, then up to three additional movers from each of the eight categories. A project appears only once across all sections. All lists keep the existing 100-star floor and 60-day activity filter; trending lists also require a complete seven-day baseline and positive growth. Show percentage growth for context, but rank by absolute gain so tiny projects cannot dominate through a small denominator.

This mix keeps a stable reference point, makes the Monday refresh visibly useful, and spreads discovery beyond categories that dominate total-star rankings. It also supplies a factual weekly-change surface without unreviewed editorial copy. Category headings link to their corresponding LLMRepos pages.

## Decisions

- **Purpose:** a useful weekly snapshot and clear doorway to the daily site. Keep the actual top 100 and contribution path. Do not duplicate the entire site or hollow the README into a teaser.
- **Subscribe CTA:** one plain sentence after the value explanation, below the main site link. Promise a short Tuesday email, explain confirmation, avoid badges/popups/repeated asks. The prototype links to a live [repo detail page with a signup form](https://llmrepos.com/repos/ollama/ollama); this is an awkward interim destination. Production should use a dedicated signup page or anchored form, then verify the form end to end before publishing the CTA. The web app currently renders the form only on repo pages; its server action returns “Signups aren't live yet” if Kit env vars are missing ([component](https://github.com/vince-lam/llmrepos-web/blob/main/src/components/NewsletterCapture.tsx), [Kit client](https://github.com/vince-lam/llmrepos-web/blob/main/src/lib/kit.ts)). Do not use the owner's old Substack as a substitute for this product's list.
- **Weekly “what changed”:** omit from the selected README until the reviewed newsletter archive exists. The Monday job replaces only `<!-- BEGIN_TABLE -->` through `<!-- END_TABLE -->` and the first `*Last Updated: ...*`; text outside those markers would survive but silently become stale ([generator](../../scraper/update_stats.py), [schedule](../../.github/workflows/update-stats.yml)). When ready, have the generator render a separate bounded weekly block from a *published, approved* issue, with issue date and archive URL. Require freshness; omit the block if no approved issue for that week. Never auto-publish an unreviewed draft. The planned newsletter source is Markdown in llmrepos-web, with owner review before sending ([newsletter spec](https://github.com/vince-lam/llmrepos-web/blob/main/docs/specs/newsletter-stack-and-loop.md)).
- **GitHub reach:** stars are bookmarks and send no notifications ([GitHub starring docs](https://docs.github.com/en/rest/activity/starring)). Visitors can opt into repository **Watch** notifications by type, including Discussions and releases ([notification settings](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications)). Discussions announcements can carry editorial updates, but only if Discussions is enabled and people explicitly watch that surface ([categories docs](https://docs.github.com/en/discussions/managing-discussions-for-your-community/managing-categories-for-discussions)). Releases are for versioned software, so do not create weekly “releases” for a data list just to reach watchers ([release docs](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)). This repo has Discussions disabled and no releases as of 18 September 2026 ([repository API](https://api.github.com/repos/vince-lam/awesome-local-llms), [releases API](https://api.github.com/repos/vince-lam/awesome-local-llms/releases)). If community conversation develops, trial one opt-in Announcements category rather than treating stargazers as a mailing list.
- **Reciprocal links:** the live site already has a GitHub link and “Suggest a repo” in its header ([site](https://llmrepos.com/), [header source](https://github.com/vince-lam/llmrepos-web/blob/main/src/app/Header.tsx)). Keep both. Add a short “Data and suggestions on GitHub” link near site methodology/footer if user testing finds the header icon obscure. Link site to repo for provenance and contributions, not as a star ask.
- **Metric:** stars show approximate interest, not subscriptions or active readers ([GitHub starring docs](https://docs.github.com/en/rest/activity/starring)). Track qualified README-to-site visits and confirmed email subscribers as funnel outcomes; star growth is a secondary discovery signal. The site loads Umami and #43 reports github.com as 73 of 445 visits last month. README links currently carry no campaign parameters. The site signup form has a `source` hidden field, but the current server action does not read or store it ([layout](https://github.com/vince-lam/llmrepos-web/blob/main/src/app/layout.tsx), [subscribe action](https://github.com/vince-lam/llmrepos-web/blob/main/src/app/actions/subscribe.ts)). Campaign query parameters in these drafts give identifiable URLs; verify how Umami reports them and wire signup source separately before claiming conversion attribution.

## Production handoff

1. Verify Kit configuration and one real double-opt-in signup. Add a direct, stable site signup destination. Use it in A's single CTA.
2. Add a maintained README template/input for A's opening and make the generator assemble it with the table/date output. Keep the table/date markers intact. Replace stale 8,600/8,500 copy and demo alt text with current, checked figures or timeless wording. Commit the template and regenerated output together; never maintain the generated section by hand.
3. Run the generator with fixture data on a temp README and compare output before/after a second run. Confirm the CTA survives Monday regeneration, table refresh stays bounded, and no diff appears on the second run. Do not run the live stats job merely to test Markdown; it writes to Turso.
4. If the editorial block is later built, add dedicated begin/end markers, a single reader of the published newsletter issue, freshness and URL checks, and a missing-issue fallback that omits the block. Test consecutive Mondays and a skipped issue.
5. Measure README campaign visits and confirmed signups against the baseline in #43. Keep the existing site-to-repo links; revisit placement only with click evidence.

## Risks

- The prototype's repo-page signup link is indirect and may fail if Kit is not configured. Do not adopt that URL as the final CTA.
- A copied weekly block outside generator control will persist after its date, which is worse than having no block.
- The 12-column-wide table is hard to scan on phones. This prototype keeps it because it is the README's current utility; production may simplify columns in a separate generator change.
